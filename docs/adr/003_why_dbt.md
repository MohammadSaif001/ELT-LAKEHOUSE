# ADR 003 — Why dbt (Planned / Future)

| Field       | Value                          |
|-------------|-------------------------------|
| **Status**  | Proposed                       |
| **Date**    | 2026-09-01                     |
| **Author**  | Mohammad Saif                  |

---

## Context

The Gold layer of the ELT-Lakehouse pipeline produces business-level aggregates
(revenue by seller, customer lifetime value, review sentiment trends, etc.)
from the validated Silver Delta tables.

Currently, Gold transformations are written as PySpark jobs inside
`src/elt_lakehouse/spark/jobs/gold_job.py`. While this works, it has drawbacks
as the number of models grows:

1. **No lineage graph** — relationships between Gold models are implicit in
   Python code, not declared.
2. **No incremental strategy** — every Gold run is a full `overwrite`; there is
   no built-in way to process only new records.
3. **No documentation layer** — column-level descriptions, tests, and ownership
   are not co-located with the SQL logic.
4. **Testing is manual** — schema tests, uniqueness checks, and referential
   integrity at the Gold level must be hand-coded in pytest.

---

## Decision

**dbt (data build tool)** is the planned transformation framework for the Gold
layer.

```
Silver Delta tables  ──► dbt models (SQL)  ──► Gold Delta tables
                         ├── sources.yml      (schema + freshness tests)
                         ├── models/gold/     (one .sql file per aggregate)
                         ├── schema.yml       (column descriptions + tests)
                         └── lineage DAG      (auto-generated by dbt docs)
```

The `dbt-spark` adapter will be used to connect dbt to the local Spark/Delta
environment.

---

## Alternatives Considered

| Option | Pros | Cons |
|--------|------|------|
| **Plain PySpark jobs** | Already in place, full control | No lineage, no built-in tests, verbose for simple aggregations |
| **SQL scripts** | Simple | No dependency management, no incremental support |
| **Apache Beam** | Unified batch+stream | Heavy; overkill for analytical aggregations |
| **dbt** ✅ | Lineage graph, built-in tests (`unique`, `not_null`, `relationships`), incremental models, `dbt docs generate`, widely adopted | Requires dbt-spark adapter; SQL-only (PySpark logic must be extracted) |

---

## Consequences

### Positive
- Each Gold aggregate becomes a single `.sql` file — readable by analysts, not
  just engineers.
- `dbt test` runs schema + data tests automatically; no extra pytest code needed
  for Gold-layer validation.
- `dbt docs generate && dbt docs serve` produces a browsable lineage graph.
- Incremental models (`strategy: merge`) eliminate full re-scans on large
  Silver tables.

### Negative / Trade-offs
- dbt is SQL-first; any Gold logic that requires Python (e.g., complex ML
  feature computation) must stay in PySpark and be called before dbt.
- The `dbt-spark` adapter requires a running Spark Thrift Server or a
  configured SparkSession — adds local setup steps.
- Two transformation languages (PySpark for Silver, SQL/dbt for Gold) means
  contributors need familiarity with both.

---

## Current State

dbt is **not yet implemented**. Gold transformations are handled by PySpark
jobs in `gold_job.py`. This ADR documents the planned migration path.

### Migration Plan (High Level)

1. Install `dbt-spark` and configure `profiles.yml` for local Delta.
2. Declare Silver tables as dbt `sources` in `sources.yml`.
3. Port each Gold PySpark aggregation to a `.sql` dbt model.
4. Add `schema.yml` with `unique`, `not_null`, and `relationships` tests.
5. Replace `gold_job.py` with a shell call to `dbt run --select gold.*`.
6. Wire `dbt test` into the CI pipeline.
